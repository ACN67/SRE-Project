# 2. 技术路线、模块依赖和运行模式

## 2.1 一条业务 Pipeline，两类消费者

```text
                 LoCoMo conversation (只有原始对话可入业务链)
                                     │
                                     ▼
                    [B] parser → SourceTurn 索引
                                     │
                                     ▼
                   [B] extract/validate → MemoryRecord
                                     │
                                     ▼
                       [C] 索引、检索及候选补充
                       (一个最终 CandidateSet)
                                     │
                   ┌─────────────────┴─────────────────┐
                   │                                   │
       [C] Vector RAG 基线                   [D] 关系与时间解析
          直接用候选 QA                     → 有效 Memory → QA
                   │                                   │
                   └─────────────────┬─────────────────┘
                                     ▼
                    [A] 统一 Python 应用层入口
                                     │
                     ┌───────────────┴───────────────┐
                     ▼                               ▼
                [E] Streamlit                    [A] 离线评测器
                 可视化页面                    + Full Text 独立臂
                                                     │
                                          Gold loader 仅用于后评分
```

**[设计]** UI 和评测是业务接口的**两个并行调用方**，不存在“先运行 Web 才能评测”。Full Text 独立读取同一原始对话；Vector RAG 和 Dynamic 在主实验中使用**同一最终检索候选与预算**，只有后者执行状态解析。所有问答臂共享底层生成模型适配器，系统提示和上下文结构的差异必须记入实验元数据。

## 2.2 推荐的最小技术栈

- **Python 3.11**；Pydantic v2（或团队经评审确定的等价模型）用于 DTO；pytest 用于测试。
- **JSONL** 用于内部 Memory/逐题结果；**JSON** 作为统一导出交付；小规模数据使用可重建的向量矩阵和本地文件，不强制数据库。
- **Embedding + 余弦相似度** 作为起始检索方案；查询条件辅助候选扩展（同主体/属性/历史状态）在 C 内实现。具体 Embedding 名称、归一化规则、文本模板在 W1 由 C 提案并记录在配置中。
- **LLM（团队暂定：DeepSeek API）**：B 的 Memory 结构化抽取、D 的复杂状态语义判断，以及 Full Text、Vector RAG、Dynamic 三种 QA 方法通过统一 Adapter 使用 DeepSeek 云端 API。A 负责共享模型 Adapter（调用配置、超时、重试、结构化输出校验、日志、Mock）；B/D/C 不自行直连或硬编码服务商。无需在成员电脑上部署大型语言模型；未来如需更换云端供应商或本地模型，须记录变更并保持业务输入输出契约不变。
- **Embedding（团队默认：本地 CPU）**：C 使用体量较小、可在 CPU 上运行的文本向量模型；模型版本、向量维度、文本模板、归一化方式和索引 hash 写入配置。无需为检索购置 GPU。
- **Streamlit 直接调用 Python service** 为首选。**不把 FastAPI/HTTP 列为 MVP 必做**；如需后续网络前后端解耦，只能增加薄适配层，不修改核心业务签名。

**为什么这样设计**：官方只有 10 段长对话，四周项目主要工作是“使用现有 LLM 构建与分析记忆”，没有训练大模型的必要。优先投入到数据真实性、动态状态规则、模块契约和可信评测，而不是 GPU 部署与模型训练。

## 2.3 模型部署选择、接口与资源约束

**课程与方案的区别**：课件没有要求本地运行 7B/8B 或更大模型，也没有要求向云端购买特定服务。**DeepSeek API（暂定）+ 本地轻量 Embedding 是本组本版默认方案**，不是课程强制规定；API 服务商可通过 Adapter 更换，具体模型 ID 尚未冻结。即使模型在云端，Web 系统仍可在本地启动并通过网络调用模型 API。

| 模块/场景 | 默认运行位置 | 模型或实现要求 |
|---|---|---|
| B：对话→Memory | DeepSeek API（暂定） | 提取结构化 JSON；由本地 Schema 校验；失败时进行有限重试或记录失败 |
| D：状态关系判断 | 本地确定性规则 + DeepSeek API（暂定） | 主体/时间/证据先规则筛选，再用 LLM 辅助语义判断；不得让 LLM 自造来源 ID |
| A/C/D：Full Text、Vector RAG、Dynamic 答案生成 | **同一个 DeepSeek 模型（暂定）和同一生成 Adapter** | 正式对照前冻结模型 ID、生成参数及调用预算；方法差异仅来自上下文和动态解析步骤 |
| C：Embedding、余弦检索 | 本地 CPU | 使用固定版本轻量 Embedding，缓存向量，保留可重建索引 |
| 全组：契约/单元/演示 Mock | 本地 | 无网络、无 API Key、无 GPU 仍能测试；真实问答演示需要配置有效云端凭据 |

**W1 必须完成的模型验证**：默认先测试 DeepSeek API，由 A 将实际 API 地址配置方式、模型 ID、超时/重试、费用预算等写入 `configs/models.yaml`（密钥仅放环境变量）；由 C 固定本地 Embedding 模型；B/D 共同验证至少一条结构化抽取与状态判断案例。若 DeepSeek 的输出格式、上下文长度或可用性不满足需要，先在组内确认替代方案，再更新配置与决策记录。优先实测并记录最长 Full Text 所需的上下文长度、真实 Token 使用量、模型超时与粗略费用；如上下文超限，预先定义截断或分块策略并在 Full Text 结果中标记，不能假装使用了完整历史。使用 API 前核实数据许可及服务条款，API Key 只放本地环境变量，不提交 Git。云端暂不可用时开发不中止：先运行 Mock/缓存测试，正式指标待真实模型运行后计算。

**接口约束**：B/D 和三种回答方法只能调用 A 的统一模型 Adapter；生成答案的模型必须一致，Memory 抽取与状态语义判断可采用同一模型或另一个经记录的型号，但不得把模型差异隐藏在对照实验中。生产与离线评测共享完全相同的推理路径。

## 2.4 数据来源与金标隔离

1. B 读取官方固定版本数据中的 `conversation` 部分，建立会话及轮次的规范化来源索引。`qa.question` 可作为运行查询；`qa.answer`、`qa.evidence`、课程自定义状态金标由 A 的 `evaluation/gold/` 读取，**不可供 B/C/D 的算法访问**。
2. 官方 `observation`、`session_summary`、`event_summary` 等辅助字段不进入主实验 Memory 抽取；如果后续采用，须标明不同实验设置，避免额外监督影响可比性。
3. 团队固定 split 写入 `configs/data_split.yaml`：`main_dev=1–4`、`extra_dev=5–8`、`test=9–10`（按固定数据快照映射到真实 `sample_id`）。三组按完整 conversation 互斥；禁止把同一 conversation 的不同 QA 拆给多个集合。所有正式指标注明属于 `main_dev`、`extra_dev` 还是 `test`，并披露扩展集是否参与过方法选择。
4. 原始会话若有图像或 BLIP caption，须在数据处理说明中明确其支持策略；不能在不说明的情况下选择性剔除难题或更改评测分母。
5. 官方 LoCoMo QA 的 `evidence` 主要是证据轮次，**不是天然的 Memory-ID 关系金标**；课程动态测试所述的相关 Memory、关系标签、最终有效 Memory 需要另行导入并记录 provenance。未收到这些标注时，正式状态判断准确率记为 **N/A (gold pending)**，开发用人工/合成数据只能给出内部测试结果。

# 3. 领域语义：状态、时间与候选的唯一解释

## 3.1 将“关系边”和“查询决策”分层（消除 RETAIN 冲突）

**[课程]** 对 Memory 进行 RETAIN、UPDATE、SUPERSEDE 和冲突处理。**[设计]** 系统内部明确使用两层对象：

**层一：`RelationEdge`（记忆间的有证据关系）**，端点是两条**不同**的 Memory，关系标签为 `UPDATE`、`SUPERSEDE`、`CONFLICT`。不存在凭空自环 `RETAIN` 边。

**层二：`MemoryDecision`（针对一次 Query/时间的使用决策）**，每条候选记忆可得到 `RETAIN`、`EXCLUDE` 或 `UNRESOLVED`，并有 `reason`。其中 `RETAIN` 实现课件的保留动作；`EXCLUDE` 仅意味着本次问题不选作有效证据，**不删除历史**；`UNRESOLVED` 保留冲突并交给 QA 处理。

输出 `ResolutionResult` 同时包含 `relations[]`、`decisions[]`、`effective_memory_ids` 与 `unresolved_conflict_ids`；**查询是否保留不是同一对事实的“第四种边”**。如果课程方最终关系 Gold 将 RETAIN 标作成对标签，A 建立明确记录的**评测映射适配层**，不擅自修改业务 Schema；拿不到老师定义时不能声称四类标签准确率可与课程金标直接比较。

### 3.1.1 UPDATE、SUPERSEDE、CONFLICT 的可执行边界

| 类型 | 判断条件 | 正例与反例 | 历史处理 |
|---|---|---|---|
| `UPDATE` | 同一主体的同一事项发生**可追踪进展或非互斥补充**；有先后或发展证据 | “申请→面试→获录用”属于同一目标的阶段演进（对应课程示例）；“申请 A、同时购买咖啡”不构成 UPDATE | 保留每个阶段与时间，不自动认定较早阶段为错误 |
| `SUPERSEDE` | 对同一主体、同一查询属性、相同适用时间范围，**新状态取代旧状态作为当前有效值**，有明确时间或替代证据 | “此前在 A 就业→已离职并转到 B”可对当前雇主 SUPERSEDE；“在 B 兼职”不必替代 A | 当前属性用新状态；历史问题仍可选择旧记忆 |
| `CONFLICT` | 在同一主体、属性、时间适用范围下互不相容，且来源/时间不能消解 | 同一时刻“A 仍在职”和“A 已离职”，又无充分解释；不同时刻的正常变化不算冲突 | 双方保留、返回理由与不确定性 |

一个事件序列**可以同时含过程 UPDATE 和某个属性值的 SUPERSEDE**：它们描述不同事实与不同属性维度，并不互斥；禁止将“所有较新事件均覆盖较旧事件”作为通用规则。不同主体、不同属性或仅表达计划而未实现的记录，不能轻率创建关系。无足够条件时**不生成猜测关系**并记录不确定性。

**确定性处理顺序**：先检查主体/属性和时间可比性；再识别明确阶段演化或替代；最后检查同一时间适用区间内无法消解的矛盾。针对同一属性、同一时点发生互斥但无法判断版本真假的情况，不允许让 `SUPERSEDE` 覆盖 `CONFLICT`。每条关系标明推断依据、原始轮次引用和方法版本。发现复杂关系环或时间反常时不进行自动连锁修订，返回 `UNRESOLVED` 并记录警告；这已满足基础冲突处理，无须图数据库。

## 3.2 最小可执行时间模型

同一个时间字段不得兼任“事实发生时间”和“系统得知时间”。统一采用：

- `recorded_at`：原始会话时间（ISO 8601 或 `null`），只表示**记录时间**。
- `event_time`：包含 `raw`、`start`、`end_exclusive`、`precision`（`instant/day/month/year/unknown`）、`resolution`（`explicit/relative/unknown`）的 **`TimeSpan`**。统一使用**左闭右开** `[start, end_exclusive)`；未知时两端为 `null`，不能填电脑当前日期。
- `query.as_of`：可选 ISO 日期；无值时 `time_mode="latest_known"`，代表**该样本截至历史结束可证实的最新状态**，不是机器真实今天。
- 对“去年”“上周五”类相对表达，以该条 source session 的 `recorded_at` 为唯一锚点；若无法明确锚定（时区、日期或语义不明），保持 `unknown` 并保留原文。

**时间比较统一解释**：LoCoMo 会话时间如无显式时区，按**同一对话内部的本地时间轴**比较，不擅自赋予 UTC 或北京时间；显式时区的值只有规范化到同一时区后才能比较。`precision=instant` 时按输入明确到的最小时间单位构造非空半开区间，例如精确到秒的 `10:15:30` 表示 `[10:15:30, 10:15:31)`。`query.as_of=YYYY-MM-DD` 默认解释为**该日结束时**的状态；若问题明确要求日内某时刻，扩充精确时间查询但保持同一套区间语义。无法判定精度时不可补足成精确时刻。

**算法底线**：

1. 年/月/日的已知表达转换成相应日历区间，如某年 → `[YYYY-01-01, next-year-01-01)`；不得把整年精度误认为 1 月 1 日发生。
2. 对 `as_of` 日期查询，只选取在该时点**有足够证据可判定有效**的记忆；事件区间只有部分重叠时，报告不确定，不任意比较。
3. `event_time` 未知，不代表“比旧记录更新”；可以参考明确的 `recorded_at` 说明披露次序，但**不得仅凭披露较晚判定事件已替代旧状态**。
4. 当前状态的失效依赖明确关系与时间证据，不能简单“最新一条覆盖所有历史”。已知替代后的旧状态仍可回答以前的问题；对“当时实际如何”和“当时已经知道什么”的区别在答案中说明，如果做不到，需标注为限制而非伪造能力。
5. 无法比较时间、证据矛盾或未解日期表达时，返回 `UNRESOLVED` / `no_evidence` 等明确结果。基础 MVP 不实现复杂双时间数据库。

**最低覆盖测试**：明确新旧顺序、某历史日期、年月粒度混合、无法锚定的相对时间、事件时间与披露时间不一致、可同时成立的两个状态、同时间冲突。D 对每个测试写出**输入、期望关系、期望有效 ID 与不确定分支**。

## 3.3 Top-K、历史召回和公平对照

状态解析必须同时看见相关历史版本，因此初始纯语义 Top-K 可能不够。**解决方案不允许 D 绕过检索模块：**

1. C 输出一个**最终 `CandidateSet`**：先语义 Top-K，再按同主体/相关属性/时间进展在允许预算内补全历史候选（可以为 0 条）；若尚未完成扩展，先提高配置 K 并用开发集验证旧/新状态召回。
2. C 的候选总数 `max_candidates`、初始 `base_top_k`、扩展规则/条数、索引指纹和排序方式写入运行配置与响应。
3. Dynamic 与 Vector RAG **共享同一个最终 `CandidateSet`**；D 只能对候选内的 ID 生成边和有效选择，不自行查询全量 Memory。因而主对照只主要改变动态处理，保留可解释性。
4. 可以单独增加固定初始 Top-K 的消融实验或更强的候选扩展实验，但必须另标名称与预算，不混入主实验结果。
5. C 在开发集统计证据 Recall@K，并展示至少一个“旧+新状态”都进入候选的用例；**没有 Gold 时可用明确标注的 Mock 事实测试，不得称真实 LoCoMo 召回已达标。**

# 4. 跨模块唯一数据契约（v1.2）

## 4.1 全局规则

- `schema_version` **统一为字符串 `"1.2"`**；本文所有 JSON 实例使用这一版本，旧 `1.0/1.1` 示例仅作为历史资料，不得混用。
- `sample_id` 是完整对话范围；跨样本 ID 不得作为合法引用。每个 `source_ref` 唯一定位 `(sample_id, session_id, dia_id)`。严格检查来源存在性。
- `memory_id` 固定算法：先对 `sample_id`、`session_id`、`dia_id`、`entity`、`attribute`、`value` 和 `content` 统一 Unicode NFC、去掉首尾空白并将连续空白归一为单个空格（`null` 保留为 JSON null）；将 `source_refs` 按 `(session_id, dia_id)` 升序排序；按这些固定字段组装对象，用 `json.dumps(..., ensure_ascii=False, sort_keys=True, separators=(",", ":"))` 得到 UTF-8 canonical payload，取 SHA-256 前 20 个十六进制字符，格式 `mem_<20hex>`。相同抽取结果与同样规范化规则重跑必须一致；**抽取内容、Prompt 或规范化变更可导致 ID 变化**，由 manifest 记录 extraction version，不保证不同抽取版本 ID 不变。完全相同 canonical payload 产生重复 ID 时可去重并汇总来源；**不同 canonical payload** 却产生同一 ID 时视为哈希冲突，必须停止并报告，不能静默覆盖。
- 数据模型存放于 `src/dynamic_memory/contracts/`；Markdown 示例不是另一个权威 Schema，任何变更须更新 DTO、示例、合同测试、`docs/contracts.md` 和版本号。
- 业务输入不得包含 Gold；非法跨样本/悬空引用是**合同错误**，不可当作正常无证据回答。
- 演示用下列 JSON 为虚构 mock，不代表真实 LoCoMo 文本或真实 Memory ID；示例短 ID 仅用于阅读，合同 fixture 必须符合实际 20hex ID 算法。

## 4.2 基本类型（字段说明）

| 类型 | 最低字段 | 关键规则 |
|---|---|---|
| `SourceRef` | `session_id`, `dia_id` | 联合 `sample_id` 定位原始轮次；同一 Memory 的证据必须可追溯 |
| `TimeSpan` | `raw`, `start`, `end_exclusive`, `precision`, `resolution` | 未知时间用空端点及 `unknown`；区间左闭右开 |
| `MemoryRecord` | `schema_version`, `memory_id`, `sample_id`, `content`, `entity`, `attribute`, `value`, `recorded_at`, `event_time`, `source_refs`, `extractor_version` | `source_refs` 非空；初期每条记忆从单一原始 session 抽取，跨 session 关系由 D 表示 |
| `QueryRequest` | `schema_version`, `query_id`, `sample_id`, `question`, `as_of`, `time_mode` | `time_mode=latest_known` 时 `as_of=null`；`time_mode=as_of` 时需给日期 |
| `CandidateItem` | `memory_id`, `rank`, `score`, `source_refs` | 同样本内有序，不重复，rank 连续正整数 |
| `CandidateSet` | `schema_version`, `query_id`, `sample_id`, `base_top_k`, `max_candidates`, `retriever_fingerprint`, `items` | `items` 是 C 生成的**完整且最终**候选集合；对基线和 Dynamic 不作二次隐式修改 |
| `RelationEdge` | `from_memory_id`, `to_memory_id`, `relation`, `evidence_refs`, `reason` | 端点不同且必须属于 CandidateSet；关系 `UPDATE/SUPERSEDE/CONFLICT` |
| `MemoryDecision` | `memory_id`, `action`, `reason` | `action=RETAIN/EXCLUDE/UNRESOLVED`；每个候选恰一条决策 |
| `ResolutionResult` | `query_id`, `relations`, `decisions`, `effective_memory_ids`, `unresolved_conflict_ids`, `uncertainty` | 有效 Memory IDs 为 `RETAIN` 决策的子集；所有 ID 在最终候选内 |
| `AnswerResult` | `status`, `answer`, `evidence_refs`, `uncertainty`, `error` | 状态 `answered/no_evidence/unresolved_conflict/error`；引用必须来自已选/保留 Memory 来源 |
| `QueryResponse` | 请求字段 + `retrieved` + `resolution` + `answer_result` | 业务层可统一序列化，E/A 均消费相同结构 |

## 4.3 函数层唯一默认接口

```python
# 类型全部从 dynamic_memory.contracts 导入；签名是目标设计，不代表已经实现

def load_conversations(path: str, split_path: str) -> DatasetBundle: ...
def get_turn(sample_id: str, ref: SourceRef) -> SourceTurn: ...
def build_memories(sample: ConversationSample) -> list[MemoryRecord]: ...
def export_memories(memories: list[MemoryRecord], path: str) -> None: ...
def build_index(memories: list[MemoryRecord], settings: RetrievalSettings) -> RetrievalIndex: ...
def retrieve(request: QueryRequest, index: RetrievalIndex) -> CandidateSet: ...
def load_candidates(candidates: CandidateSet, index: RetrievalIndex) -> list[MemoryRecord]: ...

def answer_dynamic(request: QueryRequest, resolution: ResolutionResult, candidates: list[MemoryRecord]) -> AnswerResult: ...
def answer_vector_rag(request: QueryRequest, candidates: list[MemoryRecord]) -> AnswerResult: ...
def answer_full_text(request: QueryRequest, sample: ConversationSample) -> AnswerResult: ...
```

**单一依赖方向**：B→C→D→A service→E / A evaluation；`answer_vector_rag` 属于 C，`answer_dynamic` 属于 D，`answer_full_text` 属于 A；A 维护共享底层生成器 Adapter 与配置但**不代写** C/D 的上下文构建。A 的 `run_query` 只编排、校验和组装，不另行执行状态推理。E 默认**直接调用 Python `run_query`**；若未来接 HTTP，路由只负责输入输出转换。评测器调用相同 `run_query` 而不是拷贝另一套计算链。

## 4.4 数据落盘、索引和重跑规则

- B 的 `memories.jsonl` 每行符合 `MemoryRecord`，课程导出 `memories.json` 是同内容的 JSON 数组；附 `manifest.json` 记录源数据 hash、抽取配置版本、样本 ID、条数。输出先写临时文件，验证通过后替换正式文件；运行失败不破坏上一次有效导出。
- Memory 重建使用完整指定集合；相同输入/配置产生相同 ID 集合，若模型非确定性导致变化，则报告 diff 并增加 `extractor_version`/manifest，不称幂等。
- C 的索引必须可从 Memory 重建。`retriever_fingerprint` 由 sorted Memory ID+内容摘要、Embedding 模型/版本、文本模板和参数计算；加载指纹不匹配的索引必须重建或拒绝加载。
- `RelationEdge` 默认是**查询输出**而非持久修改原始 Memory；为演示与复现将对应 QueryResponse 保存在逐题 JSONL 中。课程若额外要求长期维护关系图，再增加可重建关系导出，不提前强制数据库与复杂事务。
- A 的每次实验写 `run_config.json`、`predictions.jsonl`、`metrics.json`、`errors.jsonl`（可空）以及代码 SHA；正式测试配置冻结后，不利用 test 金标调试/改 Prompt。

## 4.5 跨模块合同与异常

- B→C：合法 Memory、真实 SourceRef、manifest、读取样例；合同测试验证来源存在和不跨样本。
- C→D：唯一最终 CandidateSet，按 ID 只读加载候选内容；D 不能扩张候选或接触全库；合同测试校验排名唯一、预算、来源和所有关系引用闭包。
- D→A：ResolutionResult 与 AnswerResult 必须通过约束校验；未确定冲突返回明确状态，禁止返回伪有效答案。
- A→E：Web 只消费 QueryResponse，并通过 B 的 `get_turn` 展示原文；Web 不自行决定状态、不读取 Gold。
- 统一可识别异常：`SCHEMA_INVALID`、`SOURCE_NOT_FOUND`、`SAMPLE_MISMATCH`、`INDEX_STALE`、`MODEL_TIMEOUT`、`MODEL_OUTPUT_INVALID`、`GOLD_UNAVAILABLE`。其中业务状态 `no_evidence`/`unresolved_conflict` 不等同程序崩溃。
- 合同变更：发 Issue/变更说明→评估上下游→双方确认→一起更新 contracts 代码、样例、测试和文档→PR；禁止以复制他人类、隐式字段兼容来临时“修复”接口。

## 6.1 A — 常珂舒：组长 + 独立评测技术模块

**独立技术任务**：初始化工程及组织统一 contracts、共享 LLM/Mock Adapter、`run_query` 编排、Full Text 基线、统一评测器、官方 QA F1 适配、Recall/状态指标计算、结果元数据及自动化测试；**管理与协调**：集成计划、会议组织、PR/接口协调和最终交付。会议纪要可由成员轮值记录。

**验收**：①新成员按 README 可安装/执行 Mock；②三个方法在同一题目配置下有独立可追踪输出；③Full Text 能按同样 QA 集合生成答案且清楚记录上下文截断；④官方 QA 评分封装通过手算固定题型案例与官方源码对照；⑤ Recall/状态评测缺 Gold 时主动返回 N/A，不能假记准确率；⑥逐题预测、运行配置、失败统计和汇总结果可以复算；⑦最终服务/Web联调并非只有组长电脑能跑。

**移交**：A 最先交 `contracts`/Mock/统一运行入口给其余成员；C、D 提交问答实现后，A 才接入统一 Runner；A 的集成不允许篡改他人模块输出。

## 6.2 B — 吴宇轩：对话与结构化 Memory

**目标**：LoCoMo 原始会话无损规范化，抽取可追溯、可重新导出且状态演化不丢失的 Memory。固定抽取窗口（推荐先按 session，长 session 再加带重复轮次的窗口）、原子事实粒度、人物/属性规范化、输出校验、重试和人工复核触发条件；所有实际决定写入 `configs/extraction.yaml`。

**验收**：①按冻结的数据映射可解析 1–10 的真实 `sample_id`，三组不重叠，`get_turn` 可回查；②缺失时间不造日期；③Memory JSON Schema 校验与回读一致；④同输入/配置重跑 ID 可核对，抽取发生变化写 manifest diff；⑤同一阶段重复事实去重不抹去原始证据，跨会话不同状态保留；⑥Gold 答案从未进入抽取输入；⑦与 C 完成至少一个 **`main_dev` 真实样例**的 Memory→检索合同联调。提交合成与真实样例的字段及来源核查报告。

**依赖/责任界限**：B 不负责状态关系推断；D 对跨 session 关系作判断。B 在 W1 提供规范化 Mock Memory 使 C/D/E 可并行。

## 6.3 C — 郭柏村：检索与 Vector RAG

**目标**：建立样本内索引，稳定返回包含旧、新相关状态的最终候选；实现不调用 D 的 Vector RAG 回答路径。冻结并记录 embedding 版本、文本编码模板、归一化、相似度、排序 tie-break（建议 score 降序、memory_id 升序）、索引 fingerprint 与重建规则；参数放 `configs/retrieval.yaml`。

**验收**：①相同配置/输入检索排序一致；②跨样本访问被拒绝；③空结果/索引过期/模型加载失败有明确路径；④`base_top_k`/`max_candidates` 及补充候选数量能在响应和配置核对；⑤状态演化 Mock 场景中能同时取到新旧 Memory，且最终 CandidateSet 同时供 Vector RAG 与 Dynamic；⑥Vector RAG 的 QA 直接用候选并跳过 `resolve`；⑦同 B 和 D 完成双向合同测试，向 A 提供候选/预测输出。

**边界**：候选扩展由 C 实现，D 不扫描全量内存；这也是主对照公平性的必要条件。

## 6.4 D — 杨林涛：时间、动态关系、有效状态及 QA

**目标**：对最终候选实施 §3 的唯一语义，给出 `RelationEdge`、逐条 `MemoryDecision`、有效集合和答案。先确定性规则（主体/属性/时间比较），再用 LLM 判断必要的语义边界；状态解析失败和模型输出非法必须可识别。

**验收**：至少覆盖①RETAIN 独立事实；②申请→面试→录用 UPDATE；③明确旧雇主被新雇主替代 SUPERSEDE；④同一时段未解矛盾 CONFLICT；⑤历史 vs 当前问题差异；⑥年月日不等精度；⑦无锚点相对时间；⑧事件/记录时间不同；⑨无证据拒答；⑩多主体隔离。所有边端点与决策 ID 必须属于 C 给的候选；Answer 的证据来源必须存在；`UNRESOLVED` 不伪装有效答案。Mock 全部通过后，至少用真实开发集样例同 C/A/E 联调并交错误案例分析。

**边界**：D 不访问完整 Memory 库或 Gold，不把查询级 RETAIN 存成自环边；评测四标签映射由 A 按教师说明独立实现。

## 6.5 E — 刘星宇：Web 与证据可视化

**目标**：Streamlit 消费同一 Python `run_query`，完整展示 Memory、候选、关系、Query 选择、答案和来源证据。提供 `sample_id` 选择、Memory 列表、提问与 `as_of` 输入、状态/时间可视化和证据跳转；关系可先用清晰表格/时间线，不强制复杂交互图。

**验收**：①只通过批准的服务调用，不复制 C/D 算法；②Mock 响应和真实开发集运行均可展示；③点击任何 SourceRef 都指向原始轮次；④ `answered/no_evidence/unresolved_conflict/error` 有明显差异；⑤没有数据、处理中、模型超时、字段失败都能正确提示；⑥有一条可复现演示路线、启动说明和截图；⑦测试集界面不显示 Gold。由 A/E 联合完成 Web+统一服务端到端验收。

# 7. 测试、评测、验收与公平性

## 7.1 层级与关键测试

1. **单元**：B 原始字段/时间提取；C 排序和过滤；D 时间关系及冲突；A QA F1/Recall/状态计算；E UI 状态映射。
2. **合同**：JSON Schema/DTO、来源引用、同样本、候选边界、统一版本、异常分支。
3. **模块联调**：B→C、C→D、D→A、A→E，各自先 Mock 再真实开发集。
4. **端到端**：开发集至少一条真实样本完成数据→Memory→候选→关系→答案→Web/离线 Runner。
5. **正式评测**：冻结代码配置后运行独立测试集（9–10），保存逐题与分题型输出，证据与动态关系 Gold 不足的指标注明 N/A。

**自动检查必须发现**：悬空关系 ID、错误引用轮次、跨样本污染、同一候选重复、非法时间区间、使用过期索引、未解冲突却给确证答案、报告说“通过”但无测试证据。

## 7.2 三路基线定义

| 方法 | 输入和流程 | QA 评测 | Evidence Recall@K | 动态状态评测 |
|---|---|---|---|---|
| Full Text | 同样本全部历史原文 → 统一生成器；记录窗口/截断 | 是 | N/A（无 Memory 检索） | N/A（无状态输出） |
| Vector RAG | 同样本 B Memory → **同一 C CandidateSet** → C 构建上下文 → 统一生成器；无 D 状态逻辑 | 是 | 是（C 候选） | N/A |
| Dynamic | **同一 C CandidateSet** → D 关系/时间/有效记忆 → 统一生成器 | 是 | 是（同候选） | 金标具备且映射明确时是 |

Vector RAG 是**以结构化 Memory 为索引对象的课程项目基线**，不是声称复现所有研究论文里的原始对话级 RAG。Full Text 的上下文 token 与检索方式不同，应记录完整成本与截断规则，不能说三方法除动态状态外完全相同。共享生成器的采样、最大输出、重试、调用失败及输入长度预算应被冻结；由于输入模式不同，Prompt 必要差异需披露。额外更强检索单列实验，避免影响主对照。

## 7.3 QA F1：严格对齐官方评测源码

**正式 QA F1 使用固定版本官方 `task_eval/evaluation.py` 中 `eval_question_answering` 行为的适配实现或经核验的直接调用**，不得使用泛化的 SQuAD Token F1 冒充官方：

- 类别 **1（multi-hop）**：按英文逗号分割预测与标准答案，针对每个 Gold 子答案取预测子项最大 token F1，再对 Gold 子项平均。
- 类别 **2/3/4（单跳 / open-domain / temporal）**：使用官方 `f1_score`（小写、移除标点和特定冠词/连词、Porter stemming、Counter 交集 F1）；其中类别 **3** 先对 Gold 以分号取第一部分。
- 类别 **5（adversarial/unanswerable）**：官方实现检查输出是否包含 `no information available` 或 `not mentioned`。**这与中文“无法回答”的直接输出并不等价**；评测臂须按官方拒答口径设置英文输出/映射，并在报告公开说明。不可答题的 UI 文案可以中文显示，但评测原始预测必须保留供复算。
- 逐题保留类别与预测、分题型得分、宏平均及总样本数；源代码可能存在实现细节缺陷，应以**冻结版本的实际行为**复现，不能静默“修正”后仍称官方分数。

官方开源源码：<https://github.com/snap-research/locomo/blob/main/task_eval/evaluation.py> 。上面是该源码当前公开版本的可核对行为；正式实验应保存使用版本的 SHA / 文件 hash。课程若另有统一 F1 脚本，以教师公布口径为准，并同时保留与官方分数的区别说明。

## 7.4 证据检索指标及状态金标

- 课程写 **Evidence Memory Retrieval Recall@K**；若课程给出**Gold Memory ID**，直接比较命中的唯一 Gold Memory；若只有官方 `qa.evidence` 轮次，必须通过 B 的 `source_refs` 计算 **Evidence-turn Recall@K**，在结果里写清标注单位，不能两者混称。
- 固定 K 的标准定义：`|Gold evidence units ∩ retrieved evidence units in first K candidate memories| / |Gold evidence units|`；计算时先把各 Memory 的 evidence units **去重为集合**，避免某轮被重复召回计多次；如果候选扩展后总数 > K，严格按排序后的前 K 计算；另报告完整 CandidateSet 覆盖率，防止不同预算混淆。
- 没有 Gold/无 evidence 的题目列入 `missing_gold`，不造零分也不默默缩小分母；每个分母/排除原因在结果中统计。可选另外报告 Hit@K，但不是 Recall@K。
- 动态判断准确率需课程金标的**评测单位**（关系对、候选 Memory 行动、或最终有效 Memory 集合）、标签定义和正确性规则；A 建立映射并在 `docs/decisions/` 留痕。无课程关系金标时仅报告合成测试成功数和待补标项目，不虚构正式 accuracy。
- 对评测集特定问题，LoCoMo 官方 QA 可以含开放知识题目，允许**由当前证据支持的事实 + 公开常识推理**形成解释；不得凭外部知识补造用户私有经历。QA Prompt 的公开常识处理策略要在三路运行中一致。

## 7.5 实验预算、失败与可重复性

每次实验固定数据版本及 split、方法名、K/候选预算、embedding/索引 hash、抽取结果 manifest、模型与 Prompt、上下文上限、生成温度/重试、随机种子（适用时）、源码 SHA。逐题记录 `query_id`、gold category（仅评分阶段）、预测、引用、状态、错误与耗时。区分**总题目数、评分成功数、失败数、Gold 缺失数**；服务失败不悄然删除，应单列覆盖率与对整体结果的影响。正式测试集（9–10）只在配置冻结后运行，尽量避免查看测试 Gold 后反向调参。

## 9.3 主要风险和约束策略

| 风险 | 影响 | 优先处理 |
|---|---|---|
| 状态语义/时间不统一 | D 的实现与 A 的评分冲突 | §3 定义与合成合同测试，老师金标最终确认 |

| 正式动态金标未到 | 状态准确率不可证明 | 提前完成评分框架，输出 pending/N/A，禁止假填 |
| LLM 输出或调用不稳定 | 抽取、状态判断或问答失败 | 输出校验、有限重试、缓存与 Mock 测试 |

**最终原则：课程需求正确、契约自洽、证据可复核，优先于功能数量和表面复杂度。**
