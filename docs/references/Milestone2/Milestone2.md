## 1. 项目背景与愿景（Vision）

在长期对话中，一个人的工作、计划和生活状态会不断变化。普通检索虽然能找到相关记录，却可能用旧状态回答当前问题，或把“准备做某事”当成“已经做过”。但旧信息也不能直接删除，因为用户仍可能询问过去的经历。

我们计划基于 **LoCoMo 长期对话数据**，开发一个能够管理结构化记忆、判断状态变化并展示回答依据的 Web 系统。项目的目标是：**让智能体不仅记得历史，还能根据问题判断哪些记忆适合用于当前回答。**

系统主要解决三个问题：

- **记忆可追溯：** 从原始对话提取事实、事件和状态，保留时间及原文来源。
- **新旧状态可区分：** 根据提问意图和时间条件，判断信息是更新、替代还是存在冲突；旧事实继续保留供历史查询使用。
- **回答可以核实：** 展示检索结果、最终使用的记忆和原始证据，证据不足时明确说明。

例如，某人在对话中先表示正在求职，后来提到已经入职。“现在在哪里工作”和“以前在哪里工作”就需要不同的证据。本项目希望处理这样的区别，并通过实验检查实际效果。

## 2. 使用对象与项目范围（Scope）

项目主要面向**用户、教师与评测人员**：前者可以浏览记忆、提出问题和查看来源；后者可以检查系统功能、测试记录和方法对照。开发团队通过统一接口协作。

### 3.1 动态记忆的主要区别

普通 Vector RAG 将检索出的 Memory 直接用于回答；Dynamic 会先检查候选之间的关系：

- **UPDATE：** 对同一事项的进展或补充。
- **SUPERSEDE：** 有明确证据的新状态替代旧状态的当前适用性。
- **CONFLICT：** 相关信息互相矛盾且暂时无法消解。
- **RETAIN / EXCLUDE / UNRESOLVED：** 根据本次问题决定采用、排除或暂不确定某条 Memory。

这些决定**只影响本次问答，不删除历史记录**。系统还需区分计划和已发生事实、事件时间和持续状态，以及“当前”和“曾经”等不同问题。

### 3.2 用户如何使用

用户在 Web 中选择对话样本后，可以直接浏览 Memory 及来源；输入问题并选择方法后，查看答案和相关候选。选择 Dynamic 时，还能查看状态关系和最终使用的有效记忆。遇到证据不足或未解决的冲突，界面会说明原因，而不是只显示一个确定答案。

## 4. 对照实验与验收目标

| 方法 | 回答时使用的信息 | 动态状态处理 |
|---|---|---|
| **Full Text** | 同一样本的原始对话历史 | 无 |
| **Vector RAG** | 检索到的结构化 Memory | 无 |
| **Dynamic** | 与 Vector RAG 相同的候选，经状态解析后选择证据 | 有 |

三种方法使用相同题集和可比较的基础问答模型设置。Vector RAG 与 Dynamic 共享最终检索候选，便于判断差异是否来自状态解析，而不是检索输入不同。

我们计划从三个方面评测：

1. **QA 表现：** 采用 LoCoMo 官方或课程规定的评分口径，报告整体和分题型结果。
2. **证据检索：** 统计 Evidence Recall@5 / Recall@10，并明确评价的是来源轮次还是 Memory。
3. **动态状态判断：** 分别检查关系、单条 Memory 决定和最终有效集合；缺少正式 Gold 时如实标注 N/A。

验收时重点检查：Memory JSON 能回读且来源有效，当前/历史/计划/冲突等问题可以复测，Web 能运行，三路实验及失败记录可以核查。实际效果以测试结果为准，不预先假定 Dynamic 一定优于基线。

## 7. 可能的问题与交付材料

主要风险包括 Memory 抽取遗漏历史事实、时间关系判断不准确、模块接口进度不一致，以及外部模型服务或正式 Gold 尚未确定。我们会优先使用开发集和 Mock 测试接口，保留错误记录；正式 DeepSeek 型号、真实 sample ID 和评分依据在确认后统一填写。测试集不用于调参。

最终计划提交**可运行的 Web、完整源码、结构化 Memory JSON、三路实验结果与分析、SRS、项目报告、展示材料和必要的开发/会议记录**。
