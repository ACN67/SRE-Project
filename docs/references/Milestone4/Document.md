**课程：** 软件需求工程

**团队：** 收手吧阿组

**成员：** 吴宇轩、郭柏村、杨林涛、刘星宇、**常珂舒**

## 1. 项目概述

本项目旨在解决智能体长期对话中的记忆更新问题：同一人物的工作、计划或生活状态会随时间变化，普通检索可能找到相关记录，却未必能判断该使用最新状态还是历史状态。如果简单覆盖旧记忆，又会使历史问题失去依据。

我们基于 LoCoMo 长期对话数据设计动态记忆管理系统，将原始对话转化为可追溯的结构化 Memory，再根据问题的时间条件识别记忆之间的更新、替代和冲突关系。系统不仅需要给出答案，还应展示所依据的记忆和原始对话。项目同时设置 Full Text、Vector RAG、Dynamic 三种回答方式，检验状态解析是否改善问答表现。

到现在中期阶段的主要成果是：我们完成了总体方案的设计，完成了需求规格与公共数据约定，建立了数据读取和来源定位能力，形成了可初步操作的 Web 记忆浏览界面，并开展了各模块的开发与基础的测试。

## 2. 系统整体架构

### 2.1 总体设计

系统采用离线记忆构建与在线问题处理分离的架构，减少用户每次提问时重复处理整段长对话的开销。数据、检索、状态判断、回答生成和 Web 展示分别承担不同职责，通过统一数据对象与服务连接。

```text
离线阶段：LoCoMo 对话 → 数据规范化 → 结构化 Memory → 检索索引
                                       ↓
在线阶段：用户选择样本并提问 → 查询意图与时间分析 → 相关候选
                                                   ├→ Vector RAG：直接回答
                                                   └→ Dynamic：状态解析 → 有效记忆 → 回答
对照路径：原始对话 ────────────────────────────────→ Full Text 回答
                                  ↓
                         统一结果 → Web 展示 / 实验评测
```

其中，原始对话与结构化 Memory 同时保留：Memory 负责提高检索和状态分析的可操作性，原始对话则作为最终可以回查的证据来源。Web 和评测程序共用同一业务结果，避免界面展示与实验统计采用不同的判断规则。

### 2.2 模块划分与职责

| 模块 | 主要设计及作用 |
|---|---|
| **数据与记忆构建（B）** | 导入 LoCoMo，保留对话轮次及来源；抽取人物、事件、状态，生成并保存结构化 Memory。 |
| **查询分析与检索（C）** | 识别问题涉及的人物、属性和时间，检索相关 Memory，并补充可能影响判断的历史候选。 |
| **动态状态解析（D）** | 分析新旧记忆的进展、替代或冲突关系，根据本次问题选择适用的记忆。 |
| **共享服务与问答评测（A）** | 提供统一的模型调用与问答入口，支持 Full Text 基线、三路结果记录和评测。 |
| **Web 可视化（E）** | 提供样本选择、记忆浏览、原文回查；后续接入问答、候选及状态关系展示。 |

各模块通过统一的数据结构交接，不直接依赖其他成员的内部实现。例如，检索模块输出有序候选，动态模块只根据收到的候选做状态判断，不自行另建一套检索流程。

### 2.3 模块衔接与设计原则

系统首先保证每条 Memory 都能定位到原始对话，再将统一格式的记忆交给检索和状态判断模块。检索结果需要保留候选顺序及其来源，动态判断只决定**本次回答**采用哪些记忆，不直接覆盖或清除旧记录。问答服务将回答、使用证据和不确定状态组织为统一结果，供 Web 与评测复用。

这种设计还有一个实际意义：如果后续发现历史问题回答错误，可以逐层检查是原始事实抽取遗漏、检索没有召回旧状态，还是状态解析时错误排除了证据，而不必重新排查整个系统。

## 3. 关键功能设计

### 3.1 结构化记忆与来源追溯

每条 Memory 记录事实内容、主体及属性、相关时间和原文来源。系统区分“已经发生的事实”“未来计划”“不确定表述”，避免把“准备入职”当作“已经入职”。来源使用样本、会话和轮次共同定位；用户或评测人员可以从一条记忆回到具体原始对话。

设计上不直接删除过时事实，也不将 Memory 永久标为“有效”或“无效”。某条记录能否用于回答，取决于当前问题。例如，以前任职过的单位可能不适合作为当前工作的答案，但仍然是历史经历问题的重要证据。Memory 构建失败或只完成一部分时，也不能将不完整结果直接投入正式问答。

### 3.2 检索、状态关系与有效记忆

用户的问题先被分析为当前状态、历史状态、状态历程或事件事实等意图，并单独处理时间条件。检索模块在指定人物的对话内寻找相关记忆，既考虑相似度，也尽量保留有关的旧阶段，避免只检索到最新记录而无法判断变化。

动态模块重点处理两类结果：

| 结果层次 | 具体含义 |
|---|---|
| **记忆之间的关系** | UPDATE 表示进展或补充；SUPERSEDE 表示有明确依据的新状态替代旧状态的当前适用性；CONFLICT 表示无法消解的矛盾。 |
| **针对本次问题的决定** | RETAIN 表示用于回答；EXCLUDE 表示本次不采用；UNRESOLVED 表示有效性暂时无法确定。 |

两类结果不能混淆：旧状态在“当前”问题中被排除，并不意味着原始记忆被删除。遇到时间不明确、尚未落实的计划或相互矛盾的证据，系统应保留不确定性，而不是强行给出确定答案。

### 3.3 问答与实验对照

系统设计了三种回答路径：

| 方法 | 使用的信息 | 目的 |
|---|---|---|
| **Full Text** | 同一对话的原始历史内容 | 作为直接利用历史文本的基线 |
| **Vector RAG** | 检索得到的结构化 Memory | 检查普通记忆检索的表现 |
| **Dynamic** | 与 Vector RAG 相同的候选，经状态判断后选择证据 | 观察动态状态处理的作用 |

为保证比较合理，三路应使用相同题集和可比较的回答模型设置；Vector RAG 与 Dynamic 尤其需要共享最终候选。计划报告问答成绩、证据检索 Recall@K、动态状态判断指标，保留逐题结果及失败原因。测试集答案和标注仅在评分时读取，不进入回答流程。

### 3.4 Web 交互设计

Web 面向演示用户提供两类操作。其一是**无需提问的记忆浏览**：选择样本、筛选记忆、查看详情并打开原始来源。其二是计划中的**可解释问答**：输入问题、选择回答方法，查看答案、检索候选、动态关系与最终采用的证据。

界面需要明确区分“没有相关记忆”“尚未完成构建”“证据不足”“时间无法确定”和“服务失败”，不能将系统错误误写为正常的无证据结果。

## 4. 典型使用场景（Use Case）

Use Case 用来说明用户提出什么需求、系统如何处理、最终能观察到什么结果，也是从需求衔接到系统设计和验收测试的依据。

| 使用场景 | 用户操作与预期结果 | 对应设计 |
|---|---|---|
| **记忆浏览与来源查看** | 选择对话，查看某条 Memory 的内容、时间及原始发言；无法定位来源时明确提示。 | 数据与来源服务、Web |
| **查询当前状态** | 提问“现在在哪里工作？”，系统结合新旧记录选择最新有依据的适用状态。 | 查询检索、动态状态解析、问答 |
| **查询历史状态** | 提问“2023 年初在哪里工作？”，系统选取当时适用的旧记录，不被后来的新状态覆盖。 | 时间分析、历史候选与有效记忆选择 |
| **处理冲突或证据不足** | 查询存在互斥信息或缺少依据的问题，界面显示冲突双方或说明无法确定。 | 冲突判断、回答状态及提示 |
| **三路实验比较** | 评测人员对同一批问题运行三种方法，查看各自回答、证据和评分结果。 | 统一业务入口、实验评测 |

**典型用例：当前状态与历史状态的区别。** 假设某人在对话中先提到在 A 公司工作，后来明确表示离职并加入 B 公司。针对“现在在哪里工作”，系统应利用后续状态及其来源回答；针对“以前在哪里工作”，则应保留 A 公司的历史证据。具体流程为：**输入问题 → 分析时间和意图 → 检索新旧 Memory → 判断状态关系 → 选择适用证据 → 展示回答和来源**。如果缺少离职日期或证据存在冲突，应说明不确定性。

从测试角度看，这个用例至少需要检查三种情况：一是最新状态具有明确的变化证据，系统能正确回答当前问题；二是用户询问变化前的时间，系统能找回旧记录；三是只有计划、时间不明确或相互矛盾的表述，系统不能凭空确定事实。这样可以把 Use Case 直接转换为后续联调时能够复现的测试场景。

| **Web 一期界面** | 已形成可运行的记忆浏览界面，支持样本选择、列表筛选与分页、详情和原始来源查看，并能提示空数据或服务异常。 |

目前的测试可以分为两个层次：一是检查某项基础功能是否按预期工作，例如来源能否准确定位、页面能否正常筛选和展示；二是在后续联调中检查整条业务流程，例如系统能否从真实对话中抽取 Memory，再通过检索和状态解析回答问题。第二类测试尚需随着模块完成逐步展开，中期报告不将两者混为一谈。
