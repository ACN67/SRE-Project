# 2. 技术路径与实现原理

## 2.1 系统处理链

```text
LoCoMo raw dialogue + QA/evidence annotations
         │
         ▼
[B] 数据适配/规范化 ──> 对话会话与逐轮索引（sample_id / session / dia_id）
         │
         ▼
[B] Memory 抽取 ─────> memories.jsonl / memories.json（结构化、可溯源）
         │
         ▼
[C] 构建检索索引 <──── 用户 Query、可选 as_of
         │
         ▼
[C] Top-K 候选记忆（包含来源、检索分数和稳定 ID）
         │
         ▼
[D] 状态解析（RETAIN / UPDATE / SUPERSEDE / CONFLICT）
         │
         ▼
[D] 依据 Query/时间选取有效记忆 → 带证据的 QA 答案
         │
         ▼
[E] Web 展示：检索项 + 关系边 + 当前有效项 + 引用轮次
         │
         ▼
[A] 统一实验入口：Full Text / Vector RAG / Dynamic 三路对照与评测
```

**推荐先完成“原始数据→Memory→检索→状态解析→回答→Web”的端到端最简链路**，再迭代提升质量；不应五人分别做完所有“高级功能”才首次联调。

## 2.2 数据输入与数据集管理

1. **原始数据**：优先使用官方 `snap-research/locomo` 仓库的 `data/locomo10.json`；课程选取的 6 段对话以**授课方名单为准**，写入 `configs/data_split.yaml`，明确每个 `sample_id` 属于 `dev` 还是 `test`。
2. **LoCoMo 官方基本结构**：记录含 `sample_id`、`conversation`（`speaker_a`、`speaker_b`、`session_n`、`session_n_date_time`；轮次中含 `speaker`、`dia_id`、`text`）、`qa`（问题、答案、类别、可用时的证据轮次），另有 observation、session_summary、event_summary 等字段。解析器只依赖实际存在的键，不能假设所有对话均含可解析的日期或证据。
3. **课程动态记忆标注**：课件要求从状态变化问题中形成“相关历史 Memory、关系、最终有效 Memory”的标注。这部分**不等同于官方 LoCoMo 自带的 QA/evidence 标注**；评测文件或教师具体规则未下发时，应标明 `pending_annotation`，可用团队自建小型开发样例先调通流程，**不得声称拥有官方状态判断标准答案**。
4. **隔离规则**：样本级隔离（按完整对话分组），不能把同一长对话的 QA 拆进 dev 和 test；测试集结果只用于最终汇报，不用于开发选择。
5. **许可与版本**：记录上游 Git 版本/下载日期、数据 checksum、许可限制；数据分发应遵守上游许可，不默认把原始全量数据提交到公开仓库。

## 2.3 Memory 表示：不可省略的技术约定

一条 Memory 应表示一项可独立理解的事实或状态，并有原文证据。推荐在仓库中保留如下 **`MemoryRecord v1` 契约**（字段含义在 `docs/contracts.md` 中最终确认）：

```json
{
  "schema_version": "1.0",
  "memory_id": "sample_001:session_3:D3:7:0",
  "sample_id": "sample_001",
  "content": "The speaker accepted a new job offer.",
  "entity": "speaker_a",
  "attribute": "employment_status",
  "value": "offer_accepted",
  "event_time": "2023-04-21",
  "recorded_time": "2023-04-23T10:00:00",
  "time_expression": "last Friday",
  "source_turn_ids": ["D3:7"],
  "source_session": "session_3",
  "extraction_method": "llm",
  "confidence": null
}
```

上述是**契约示例，不是 LoCoMo 原始数据**。其中：

- `memory_id` 在同一抽取配置下应稳定且唯一；`sample_id` 必须存在，避免不同对话之间误检索。
- `source_turn_ids` 必须使用原始 `dia_id`，允许多证据轮次；应能够从索引中回查原文。
- `event_time` 表示**事件发生时间**，`recorded_time` 表示**对话记录时间**，不能混为一谈；无法确认时用 `null` 并保留原始时间表达，不可猜造日期。
- `entity`、`attribute`、`value` 使用约定的规范化形式；自然语言原句保存到 `content`，必要时增加 `raw_quote`。
- 不建议在原始 Memory 中直接写永久性的 `state: active/inactive`。**有效性依赖问题和查询时间**，同一条记忆对“现在”和“过去”的提问可以有不同有效性。
- 抽取失败或证据不足应输出可诊断状态，不能创建没有来源的“记忆”。

**存储方案 [技术提案]**：JSONL（便于流水处理）作为中间存储、JSON 数组作为课程导出格式；初期使用本地文件与轻量索引足够，不强制引入数据库。若引入 SQLite/向量数据库，只视为内部实现，导出格式必须保持不变。

## 2.4 Memory 抽取方法

推荐管线：会话解析 → 按窗口或会话切块（保留原始 `dia_id`）→ 规则/LLM 抽取事实、实体、时间与状态 → 字段验证 → 去重与规范化 → 输出 Memory。

- Prompt/规则输入应包括原文、说话者、会话时间和轮次 ID。
- LLM 采用严格结构化输出；字段无法确定时保持空值，不能补写事实。
- 对重复事实可去重，但必须保留被合并项对应的全部证据轮次。
- 对状态演化中的**旧状态不能删除**；历史保留与有效状态选择属于后续模块。
- 必须支持仅使用少量固定样例和 Mock LLM 的本地测试，不依赖在线 API 才能测试解析器。

## 2.5 记忆检索方法

**基础方案 [技术提案]**：文本 Embedding + 余弦相似度排序，按 `sample_id` 过滤、返回 Top-K。数据规模有限时可先用内存矩阵检索；FAISS、BM25 或混合检索可以作为可选优化，**不是必做前提**。

检索必须保证：

- 仅检索指定对话内的记忆，杜绝跨对话污染。
- 返回稳定 `memory_id`、排名、分数、原始来源，不直接生成答案。
- `top_k` 可配置，结果排序稳定；空检索结果应返回 `[]`。
- 相关时间可以参与检索/重排，但**不得提前删除历史旧状态**，否则 D 无法正确分析替代关系。
- 开发集上通过正式标注或人工固定样例评估证据命中，而非只凭表面语义“看着相关”。

## 2.6 动态状态解析（本项目最关键的差异点）

推荐 D 的逻辑分三步：

1. **Query 分析**：抽取相关实体、属性、问题类型（当前/历史/进展）、明确的时间条件 `as_of`（如有）。
2. **状态关系判定**：对同一主体且相同或相关属性的候选 Memory 按时间与含义比较，得到有证据的关系边。
3. **有效性选择**：面向本次 Query 选择有效 Memory，保留旧状态用于历史问题、更新轨迹和证据展示。

| 标签 | 判定原则 | 预期处理 |
|---|---|---|
| `RETAIN` | 事实在该查询条件下仍成立，或不需要被更新/排除 | 纳入有效证据集合 |
| `UPDATE` | 状态延续并发展，如申请→面试→录用 | 保存演化关系；选择与问题时间匹配的阶段 |
| `SUPERSEDE` | 新信息替代旧信息对**当前属性**的有效性 | 当前查询优先新状态；旧状态仍可用于历史查询 |
| `CONFLICT` | 两个主张不可同时成立且不足以据证消解 | 保留冲突双方与理由，允许“无法确定” |

**关键约束**：不能简单地“时间最新就正确”。例如事件发生时间与说话时间不同、说话者转述、否定、计划未完成、查询过去日期、同时兼职等都可能使“最新覆盖”失败。无法消解的冲突不得悄悄选一条。

建议状态输出为**查询级 `ResolutionResult`**，不要直接篡改 Memory 原始记录。状态关系可以是有向边 `old_memory_id -> new_memory_id`，并带 `relation`, `reason`, `evidence_turn_ids`, `confidence`。需要保留无关系的独立事实。

## 2.7 生成答案与原始证据

基于 D 输出的有效 Memory 列表、问题和时间条件构建回答；回答逻辑由 D 负责，模型调用接口可以共享公共 Adapter。

- 输入仅允许携带本对话的相关记录，不把其他 sample 的历史送入模型。
- 输出最少为 `answer`、`effective_memory_ids`、`evidence_turn_ids`、`uncertainty`。
- 若问题无法从证据回答，输出明确的未知/证据不足；不要凭常识填充用户私有事实。
- `as_of` 必须影响有效记忆判断；查询过去状态时应能返回当时的状态。
- Web 显示的证据来源必须由 ID 追踪得到，禁止生成不存在的“引用”。

## 2.8 Web 与服务边界

**推荐方案 [技术提案]**：Python 统一后端；FastAPI 提供 API，Streamlit（或轻量前端）提供 UI。该组合易于五人分工、较容易快速演示。**框架是否最终采用由第一次技术评审决定。**

界面最小功能：选择 `sample_id` → 浏览 Memory → 输入问题/可选查询时间 → 运行查询 → 查看答案、Top-K、有效 Memory、状态边及证据原文。加载中/失败/空结果也需要可识别。

Web 不应重新实现检索或状态算法，而应只调用统一服务接口；评测脚本与 Web 应调用同一个核心服务，以避免“演示版”和“实验版”产生不同逻辑。

## 2.9 评测设计与对照公平性

**课程明确的三项指标**：QA F1、证据 Memory 检索 Recall@K、动态状态更新判断准确率。**课程指定基线**：Full Text 与 Vector RAG。

| 方法 | 输入路径 | 是否检索 Memory | 是否动态关系解析 | 技术负责人 |
|---|---|---|---|---|
| Full Text | 同一对话的原始历史文本→回答 | 否 | 无单独解析步骤 | A |
| Vector RAG | B 的 Memory → C 检索→直接回答 | 是 | 否 | C（A 负责统一运行） |
| Dynamic（本系统） | B 的 Memory → C 检索→ D 解析→回答 | 是 | 是 | B/C/D（A 负责统一运行） |

**评测规则建议 [技术提案，须以授课方标准为准]：**

1. **QA F1**：英文答案可采用统一小写、去标点及冠词、空白标准化后的 token-level precision/recall/F1；多答案、不可回答题须单独定义，并对所有方法保持一致。记录逐题分数和宏平均，不把 LLM 自评当作 F1。
2. **Recall@K**：若课程提供 Gold Memory IDs，则逐题算 `|Gold ∩ Retrieved@K| / |Gold|` 再宏平均；如仅有官方 `qa.evidence`（对话 `dia_id`），必须通过 Memory 的 `source_turn_ids` 映射并另行报告**证据轮次覆盖率**。避免把“问题至少命中 1 条证据”的 Hit@K 冒称 Recall@K；两者可同时报告但需注明。
3. **状态更新判断准确率**：课程若提供关系/最终有效 Memory 标注，应按照授课方定义计算；若没有，应分别报告开发集上**关系标签准确率**与**有效 Memory 选择准确率**的自建评测，声明来源和样本量，不能宣称是课程正式成绩。
4. **可比性**：同一 QA 集、数据切分、模型/调用设置、答案归一化和评价脚本；记录三路输入的上下文 Token 数、截断情况、模型及成本。Full Text 可能受上下文窗口限制，若发生截断必须记录，不可隐去。
5. **避免泄漏**：测试集不用于 Prompt/阈值优化；正式测试前冻结相关代码和配置，并输出 commit SHA、run ID、时间、版本与随机种子（如适用）。
6. **无标注情况**：可先运行流程检查和开发集自定义测试，但“未提供官方标注”应在报告中写为限制，不得填造准确率。

**A 的统一评测入口**应能按同一问题集运行三路系统，并输出逐题 JSONL、汇总 JSON/CSV 和运行元数据。失败题必须记录错误类型及总样本统计，不能从分母中悄悄删除。

# 3. 从技术路径推导仓库结构

## 3.1 模块边界如何对应文件夹

需求按数据流自然拆为 B（建 Memory）、C（检索）、D（状态与 QA）、E（用户交互）、A（框架/评测/主流程）。为让每个人能独立开发，再增加公共 Schema、基础工具及自动化测试目录。**代码的物理结构应服务于数据契约，而不是先建一堆文件夹再寻找职责。**

| 数据流中的责任 | 对应主要目录 | 必须经过的交接 |
|---|---|---|
| 数据导入/结构化记忆 | `src/dynamic_memory/data/`、`memory/` | `MemoryRecord` JSON |
| Top-K 检索 | `src/dynamic_memory/retrieval/` | `RetrievalResult` |
| 状态解析及问答 | `src/dynamic_memory/reasoning/`、`qa/` | `ResolutionResult`、`AnswerResult` |

# 4. 统一数据契约、模块接口与联调机制

> **本章是并行开发的前置条件。** 建议在第 1 周第一次技术评审就定稿 `contracts v1`；全组不得在接口未对齐时各自定义不同的输入输出。

## 4.1 基本约束

- 全部业务数据的 `sample_id`、`memory_id`、`source_turn_ids` 类型保持一致（字符串 / 字符串数组）。
- 全部时序字段采用可解析 ISO 8601 字符串或 `null`；保留原始时间表达，不能自行猜时区。
- Query 是**查询级**对象；Memory 是**事实级**对象，关系和有效性是**查询级**结果，不要在存储层永久覆盖旧事实。
- JSON 中允许可选字段，但必填字段不得临时改名；所有接口必须对“无结果/未知/错误”有明确定义。
- 所有输出都应该包含足以追溯的 ID，不允许只交付自然语言描述。

## 4.2 接口数据结构（v1 提案）

**A. MemoryRecord**：见 §2.3，最少包含 `schema_version`, `memory_id`, `sample_id`, `content`, `entity`, `attribute`, `value`, `event_time`, `recorded_time`, `source_turn_ids`, `source_session`。其中时间或具体属性不可得时允许 `null`，但来源 ID 与内容不可缺失。

**B. QueryRequest**：

```json
{
  "query_id": "q-demo-001",
  "sample_id": "sample_001",
  "question": "What is the person's current employment status?",
  "as_of": null,
  "top_k": 8
}
```

`as_of=null` 表示询问由问题语义和可用对话上下文确定的“当前状态”，**不应使用运行当天真实日期去覆盖 LoCoMo 历史场景**；“当前”默认指输入对话的最新已知时间。如问题明确给出过去日期，则按该日期处理。

**C. RetrievalResult（单项）**：

```json
{
  "memory_id": "sample_001:session_3:D3:7:0",
  "score": 0.82,
  "rank": 1,
  "source_turn_ids": ["D3:7"]
}
```

完整检索响应包含 `query_id`, `sample_id`, `items: [...]` 和 `retriever_version`；返回排序、分数含义和总数定义。分数不一定是概率，Web 不得显示成“82% 正确”。

**D. ResolutionResult（查询级）**：

```json
{
  "query_id": "q-demo-001",
  "relations": [
    {
      "from_memory_id": "memory_old",
      "to_memory_id": "memory_new",
      "relation": "UPDATE",
      "reason": "The new statement describes a later stage.",
      "evidence_turn_ids": ["D2:8", "D3:7"]
    }
  ],
  "effective_memory_ids": ["memory_new"],
  "unresolved_conflict_ids": [],
  "warnings": []
}
```

`RETAIN` 可作为记录的查询级保留判定，或用 `effective_memory_ids` 表示；**具体编码方式须在 `contracts.md` 中定稿**。不要为了填满关系边而为独立事实制造虚假边。

**E. AnswerResult / QueryResponse**：

```json
{
  "query_id": "q-demo-001",
  "sample_id": "sample_001",
  "question": "What is the person's current employment status?",
  "answer": "The person has accepted the new job offer.",
  "retrieved": [{"memory_id": "sample_001:session_3:D3:7:0", "score": 0.82, "rank": 1, "source_turn_ids": ["D3:7"]}],
  "relations": [],
  "effective_memory_ids": ["sample_001:session_3:D3:7:0"],
  "evidence_turn_ids": ["D3:7"],
  "uncertainty": null,
  "warnings": []
}
```

所有示例均为**自造结构样例**，只用于说明接口，不可作为真实数据或实验结果。

## 4.3 代码层公开接口（推荐签名）

```python
load_dataset(path: str, split_config: str) -> DatasetBundle
build_memories(sample: ConversationSample) -> list[MemoryRecord]
retrieve(request: QueryRequest, memories: list[MemoryRecord]) -> RetrievalResponse
resolve(request: QueryRequest, retrieved: RetrievalResponse, memories: list[MemoryRecord]) -> ResolutionResult
answer(request: QueryRequest, resolution: ResolutionResult, memories: list[MemoryRecord]) -> AnswerResult
run_dynamic(request: QueryRequest) -> QueryResponse
run_baseline(request: QueryRequest, method: str) -> QueryResponse
```

> 以上为**预期 API 设计**，不是已写好的函数。实际可选择类/异步函数；一旦评审通过，参数语义、返回字段和异常类型即成为契约，需通过自动化合同测试。

## 4.4 HTTP API（E 对接服务的初步方案）

| API | 用途 | 负责人 |
|---|---|---|
| `GET /health` | 服务存活、组件可用状态 | A/E |
| `GET /datasets` | 返回已加载的样本与分组，不包含测试集标准答案 | B/E |
| `GET /datasets/{sample_id}/memories` | 分页读取结构化 Memory，可查来源 | B/E |
| `POST /query` | 接受 QueryRequest，返回统一 QueryResponse | A/D/E |
| `GET /datasets/{sample_id}/turns/{dia_id}` | 对应原文证据 | B/E |

若提供数据构建/实验执行 API，须考虑耗时、超时与权限；**评测优先使用离线 CLI**，避免 Web 请求超时。E 不直接读写原始数据格式，也不负责提供“真值答案”给用户界面。

## 4.5 接口交接与变更流程

1. **先交 Mock，再交真实实现**：第 1 周由 A 建立 `tests/fixtures/` 固定输入输出样例，B/C/D/E 分别对这些样例测试。
2. **B→C**：交付 Memory JSON + schema 验证 + source lookup；C 不直接解析 LoCoMo 生数据。
3. **C→D**：交付有序 RetrievalResult（稳定 ID、rank、score、来源）；D 不自建另一套检索索引。
4. **D→A/E**：交付 QueryResponse、关系边、有效记忆 ID 与证据轮次；A 用于统一评测，E 用于前端展示。
5. **A→全组**：交付统一配置、入口和测试结果；不能未经评审修改各模块业务含义。
6. **接口变更**：提出 Issue → 说明旧/新字段、影响模块与兼容办法 → 两侧负责人确认 → 同一 PR 中更新 `contracts.md`、Schema、样例与合同测试 → 合并。
7. **依赖阻塞**：等待其他人实现期间使用已通过合同测试的 Mock；不得复制或私改他人的内部函数来绕过契约。

## 4.6 例外与错误规范

- 统一类型：`DATA_INVALID`, `MEMORY_EXTRACTION_FAILED`, `INDEX_NOT_READY`, `NO_EVIDENCE`, `LLM_TIMEOUT`, `STATE_UNRESOLVED`, `INTERNAL_ERROR`。
- `NO_EVIDENCE`、`STATE_UNRESOLVED` 不一定属于 HTTP 5xx；应作为业务状态供页面显示。
- 所有异常保留 `query_id` 和 `sample_id` 以便排查；日志不得包含真实 API Key。
- 第 1 周必须决定是否区分 `status`、`error_code` 与 `warnings`；示例 JSON 已预留 `warnings`，正式 Schema 应补齐错误分支。

# 5. 五名成员的目标、责任边界与验收

## 5.1 通用“完成定义”（Definition of Done）

每位成员提交模块时至少满足：

1. 代码通过仓库约定的格式/静态检查和自动化单元测试；没有把本地环境路径硬编码在业务逻辑中。
2. 依照 `contracts v1` 完成输入输出，能通过已有合同测试；至少覆盖正常、空数据、异常和边界用例。
3. 提供 `README` 或 `docs` 中可复现的运行命令与示例结果；所需外部模型/密钥明确列出且有 Mock 路径。
4. 提交独立 Git 分支与 PR，列出修改文件、测试命令、实际输出和已知问题。
5. 由接口下游和组长进行必要审查；验收失败的模块应说明阻塞原因与修复计划，不能仅以“代码已提交”宣告完成。

## 5.2 A（组长）：仓库框架、Full Text、评测、主流程与最终集成

**工作目标**：承担独立且可测试的技术工作（约五分之一核心开发），同时保证其余四个模块能够在同一工程中协同运行。

**负责**：仓库初始化、依赖/配置、共同 Schema 主维护、主流程编排、Full Text 基线、统一实验运行器及三项指标的评测脚本、CI/集成测试、最终集成及交付统筹；组织每周会议，保存过程材料。

**不负责**：替 B 编写 Memory 抽取逻辑、替 C 实现检索算法、替 D 实现状态判定算法、替 E 实现完整 UI；发现问题需分配归属并督促修复。

**验收证据**：

- 新成员可按文档创建环境，运行 Mock 全链路与测试；GitHub 私有仓库、基础权限和主分支规则正常。
- `full_text` 方法可在同一题集上运行，输出逐题答案和可追踪元数据；历史过长时报告截断/失败情况。
- 统一 Runner 可以选择 `full_text`、`vector_rag`、`dynamic` 并得到规范化结果。
- QA F1、Recall@K 和状态判断指标在**固定合成样例**上通过可手算的单元测试；标注缺失时拒绝假装计算正式成绩。
- 能生成逐题 JSONL 和汇总统计，并保存模型/参数、数据版本、代码 SHA；对错误题统计透明。
- 最终系统集成测试和 Web 演示可复现。组长的评测工作不应只是替其他成员运行命令。

## 5.3 B：LoCoMo 解析与 Memory 构建

**工作目标**：把课程数据可靠转换为可被检索的、有时间和来源证据的结构化 Memory。

**负责**：数据格式适配、会话轮次索引、时间与说话者标准化、Memory 抽取、字段校验、去重、导出和来源回查。

**验收证据**：

- 能按配置解析课程指定对话；`sample_id` / `session` / `dia_id` 映射正确，没有跨样本串联。
- 在至少一组固定开发样例中，事实提取的主体、内容、时间、来源符合预期；无法推断的时间保留 null。
- JSON Schema 校验通过，Memory ID 唯一且可重复，导出后重新加载字段一致。
- 任意 Memory 可回查原始对话；包含多个原始证据时 ID 不丢失。
- 提供正常输入、缺字段、重复事实、时间模糊、空数据等单元测试。
- 与 C 完成一次真实 Memory→检索联调，交付样例数据与接口说明。

## 5.4 C：Memory 检索与 Vector RAG 基线

**工作目标**：从 B 的 Memory 中召回与问题相关、足以支持后续状态判断的候选记忆，并实现“不做状态关系判断”的 RAG 对照。

**负责**：Embedding/相似度与索引、查询处理、Top-K 排序、检索统计、Vector RAG 基线；可选实现 BM25/混合检索。

**验收证据**：

- 在固定 Mock Memory 上能检索到预期 Top-K；相同输入结果可复现，`sample_id` 过滤严格生效。
- 按 `RetrievalResponse` 返回完整 ID、分数、名次和来源；无匹配时返回空集合并正确提示。
- 检索不能只保留时间最新项；历史与新状态均能作为候选送入 D。
- Vector RAG 可直接基于检索内容调用统一回答接口，**不调用 D 的状态关系解析**。
- 记录索引构建方法与配置；能向 A 提供统一检索输出和 Recall@K 评测输入。
- 与 B、D 各完成一次接口联调，并提交相应测试记录。

## 5.5 D：动态状态解析与基于证据的 QA

**工作目标**：将检索到的多条历史记忆解析为面向问题的有效状态，以可追溯证据回答。

**负责**：Query 时间/主体分析、RETAIN/UPDATE/SUPERSEDE/CONFLICT 关系判断、有效 Memory 选择、问答生成与不确定性处理。

**验收证据**：

- 至少通过以下合成用例：独立事实保留、连续状态更新、新状态替代旧状态、无充分证据的冲突、历史时间查询、证据不足拒答。
- 在“现状问答”与“某历史时点问答”下能给出不同且合理的有效 Memory 集合，不永久覆盖旧 Memory。
- 冲突未解时返回双方证据与 `uncertainty`，不得凭“最新日期”强行消解。
- 返回完整 `relations`、`effective_memory_ids`、答案及原始 `dia_id`，不存在的 ID 会导致测试失败。
- 模型调用失败/格式错误时可诊断；通过 Mock 可稳定复现状态解析流程。
- 与 C、A、E 完成接口联调，向 A 提供可评测的状态/QA 结果。

## 5.6 E：Web 与交互可视化

**工作目标**：把完整业务流程变成可运行、可解释、可演示的 Web 产品，而不是静态截图。

**负责**：前端页面、服务 API 适配、数据选择与 Memory 浏览、问题输入、结果及状态关系/证据可视化、用户可读的错误提示。

**验收证据**：

- 能选择样本、显示 Memory 列表和来源；点击证据可定位到对应原始轮次。
- 用户输入 Query 后页面展示答案、检索排序、有效 Memory 和关系/冲突信息。
- 对“无结果、接口失败、模型超时、状态未决”有清晰反馈，不以假数据冒充运行结果。
- 使用 Mock API 可独立测试；连接真实后端后同一示例能正常运行。
- 有至少一条端到端演示路线和可复现的运行说明/截图；不需要在页面中展示测试集标准答案。
- 与 A/D 完成真实服务接口验收，记录兼容性问题及修复证据。

| 交接项 | 提供者 | 使用者 | 联调/合同测试负责人 |

| 模块集成测试 | B→C、C→D、D→A/E | 真实模块输出可被下游直接消费 |
| 端到端测试 | LoCoMo→Memory→检索→状态→答案→Web | 至少一个固定案例从导入到证据展示成功 |
| 实验评测 | QA F1、Recall@K、状态指标；三路对照 | 完整逐题结果、汇总和运行元数据可复算 |
| 交付验证 | 新环境按 README 运行、报告一致性、Git/材料齐备 | 其他组员可在明确依赖条件下复现 |

**必须有的合成测试案例**：申请→录用→入职；失业→新业务开启；同一属性互相矛盾；“去年做什么”而不是“现在做什么”；提问缺少证据；混合多个实体；一条事实引用多个原始轮次；跨样本同名人物。**这些是测试用的示例，不是对真实 LoCoMo 样本的断言。**

# 7. 工作报告与验收报告：规范、模板与 AI Agent 提示词

## 7.4 模块移交与验收流程

```text
负责人完成代码与自测
     ↓
提交 PR + 工作报告 + 真实测试输出
     ↓
合同测试（上游/下游双方）
     ↓
独立审查者生成验收报告
     ↓
通过 → 合并；有条件通过 → 记录条件；不通过 → 修复后复验
     ↓
A 进行统一集成与系统级回归
```

报告经 AI Agent 撰写后，**原负责人仍需逐项核对**；AI Agent 的报告不替代 Git 提交、真实运行日志和课程要求的个人贡献证明。

# 8. 整体性要求、风险与完成标准

## 8.1 全组统一要求

1. **需求先于实现**：新增技术只要不能提高 FR 覆盖、可靠性或评测可信度，就不在 MVP 阶段优先开发。
2. **契约先于并行**：任何跨模块 JSON 字段、接口语义、状态枚举、时间定义必须由全组统一，不能独立改名。
3. **证据先于结论**：每项“已实现、已测试、已提升”都应有真实代码、命令、日志或实验文件作为依据。
4. **历史事实不可被覆盖**：状态更新不是删除旧记忆；必须兼容历史查询和不确定性。
5. **实验公平性**：同数据切分、同度量脚本、同模型设置，明确标注来源，禁止测试集泄漏和选择性排除失败样本。
6. **资源可控**：设计时估算 API 成本与运行时间，尽可能缓存确定性中间产物；禁止提交密钥。
7. **组长有技术贡献**：A 负责 Full Text 基线、评测系统与主流程，不能仅充当管理或报告汇总人。
8. **最后一周用于集成与交付**：新增扩展功能必须经过风险评估，不得影响已经通过的核心流程。

## 8.2 风险登记（首版）

| 风险 | 影响 | 处理原则 |
|---|---|---|
| 课程指定 6 段名单/动态标注未收到 | 无法做正式状态关系评测 | 先使用开发样例验证流程；向授课方确认；标明待确认 |
| 第 2 周课程中期要求与内部展示计划冲突 | 里程碑漏交风险 | 向教师核实，按正式课程通知调整安排 |
| 成员各自设计 Memory 字段 | 无法联调 | W1 冻结 contracts v1，合同测试阻止不兼容合并 |
| LLM 输出格式不稳定/费用超预算 | 数据抽取或 QA 失败 | 输出校验、有限重试、缓存和 Mock 离线测试 |
| 时间解析不准确 | 旧状态误判成新状态 | 记录事件/会话双时间和原始表达；不确定时不强行覆盖 |
| 测试集反复调参 | 指标失真 | 冻结配置后统一最终测试，保存运行元数据 |
| 第 4 周才首次联调 | 集成延期 | W1 Mock 联调、W2 真实开发样本全链路 |

## 8.3 项目最终完成（Definition of Project Done）
