## 2. 最新内容改变了哪些开发安排

### 正式索引输入改了

旧设想是“拿一份记忆列表直接建索引”。v2.2/G-02 明确：

```python
build_index(artifact: MemoryArtifact, settings: RetrievalSettings) -> RetrievalIndex
```

`MemoryArtifact` 包含记忆和构建清单（数据版本、抽取版本、是否完整等）。正式使用时由 B 的严格 loader 提供，不是 C 自己读取任意 JSON 后声称已验证。C 必须调用完整性检查，拒绝 partial/failed 产物，记录 `source_manifest_fingerprint`；数据、抽取、模型或检索设置改变时拒绝旧索引或要求重建。已有 `embed_memories(list)` 仍可作为内部编码工具，不是正式建索引入口。

### A 的查询入口已经可以接收 C

A 分支的 `prepare_shared_query(request, analyzer)` 接收 C 的分析函数，负责统一校验、快照和三路错误/时间冲突早停，不识别语义，不应重写它。C 提供 `analyze_query` 或样本词表分析器的可调用方法。

本轮在内存中读取 origin/A 的真实 `query_conditions.py`，接入当前 C 分析器，验证当前状态、历史经历、明确日期、日期冲突、带显式日期的相对时间五类合成输入：**5 PASS**。这只验证 A/C 查询条件边界，未验证索引、问答、Web 或完整真实链路。

### 需要更早做模块交接

A 已经准备了可注入的检索、候选加载和 Vector QA 端口；C 现在更需要提供能被接入的模块，而非继续只做独立演示。B 的真实产物尚未准备好时，用严格标注的合成 `MemoryArtifact` 完成开发，不能让等待 B 阻塞所有实现。

### C-03：可保存、可重新加载的样本内索引（最高优先级）

通俗目标：把一份完整记忆转换成向量，并记住“每个向量对应哪条记忆、来自哪个版本”。

1. 新增索引模块，遵守 `MemoryArtifact` 正式签名；先用有效合成产物开发。
2. 复用现有 Embedding，一次构建编码，加载/连续查询不重复编码整库。
3. 保存 memory_id 顺序、向量矩阵、样本身份及源清单指纹；允许合法零条记忆，不能把空集当构建失败。
4. 索引指纹包含源清单/记忆集合身份、模型不可变版本或本地权重摘要、编码方式/Prompt、检索参数及相关实现版本。现有 `configuration_fingerprint` 单独不足以证明模型权重身份。
5. 本地文件保存，失败不破坏上一份有效索引；读取时校验形状、有限值、记录对应及版本，不使用不可信 pickle。
6. 新增加载并核对索引的入口，供 A 的 `load_verified_index` 适配：区分缺失、过期、样本不符等稳定错误。

建议文件：`retrieval/index.py`、相应单元/合同测试。内部索引类型由 C 定义，不复制公共业务 DTO。格式可先用 JSON 元信息 + NumPy 数组，无需部署向量数据库。

通过标准：重载后向量与 ID 对应不变；跨样本拒绝；partial 被拒绝；源产物/模型/参数变化可检测；正常空索引可以安全查询。

### C-04：基础检索与候选加载（最高优先级）

通俗目标：输入问题，从该样本找到最相关的几条记忆。

1. 实现 `retrieve(request, analysis, index) -> CandidateSet`：先校验请求、分析和索引身份，再编码问题，计算相似度。
2. 默认取 Top-8；不足 8 条按实际数量返回；分数降序，同分按 memory_id 稳定排序。
3. 构造现有 CandidateSet/CandidateItem，rank 从 1 连续编号，带真实 source_refs，基础候选标记 semantic。
4. 实现 `load_candidates(candidates, index)`，严格按 rank 返回完整 Memory；校验样本、索引指纹、来源、重复/不存在 ID。
5. 无候选不是服务故障；模型加载/编码失败也不能假装成无证据。

通过标准：固定输入重复查询及保存重载后候选一致；不跨样本；相似度已知的合成向量测试排序正确；完整 Memory 与候选 ID/来源逐项一致；输出通过 A 的边界校验。

### C-05：补充历史候选（高优先级）

通俗目标：避免只找到最新工作，却漏掉判断变化必需的旧工作和离职记录。

1. 以首轮候选的主体/属性等已证实信息寻找相关历史，补充在 C 内完成，D 不绕过检索扫描整库。
2. 不删除旧状态，不按“记录更晚”直接判为当前有效；有效性判断交给 D。
3. 去重、稳定排序并截断，默认最终最多 12 条；补充项标记 history_expansion。
4. 保存 initial_topk_ids、expanded_ids、final_candidate_ids 或等价日志；纯向量 Top-8 单独保留，作为可选消融。
5. 与 A 约定同题两路消费的候选快照/复用方式；不能只因为两路都调用同一个函数，就未经验证宣称拿到同一份候选。

通过标准：合成“在 A 工作→离职→在 B 工作”、计划取消、开店关闭样例包含必要历史；不超过预算；Vector RAG 与 Dynamic 的候选 ID、排名及来源一致。

### C-06：Vector RAG 回答（高优先级）

通俗目标：把选出的记忆交给统一回答模型，给出有来源的答案。

1. 实现 `answer_vector_rag(request, analysis, candidates) -> AnswerResult`，通过实例/工厂注入 A 的共享 Runtime 和运行身份。
2. 复用 A 的 QA Prompt/生成参数及预算处理模式；参考 A 的 Full Text 实现，不把原文上下文选择规则机械照搬到记忆上下文。
3. 按候选顺序组织内容、时间及来源，在完整输入预算内优先保留高排名的完整项。
4. 记录实际输入的 used_memory_ids、context_source_refs、排除 ID 与截断原因；答案引用不能越过实际上下文。
5. 不调用 D 的 resolve，不自行判定 SUPERSEDE 等关系；空上下文、时间问题、Provider 失败按合同区分。
6. 先用 Mock/Fake 验证，再在显式真实模型配置下做少量开发集检查，不自动批量调用收费 API。

通过标准：A 的调度器可注入 C 的三个检索/回答端口；回答来源可回查；候选预算与实际生成上下文区别可核对；无 D 模块也能运行 Vector RAG。

### C-07：真实样本联调与 Embedding 选择（必须交付）

通俗目标：证明模块在真实数据上能工作，而非只在自己编的句子上工作。

1. B 提供一个 main_dev 样本的完整 MemoryArtifact 及严格 loader；C 核对样本、来源、构建身份并建立索引。
2. 与 A 一起通过独立评测路径计算 Evidence-turn Recall@5/@10 和完整候选覆盖；测试 Gold 不进入检索，不在 C 私设 Gold loader。
3. 至少检查当前/历史/经历/事件、空结果、多人隔离与时间冲突。区分 B 未抽出、C 未召回、QA 上下文未包含三类失败。
4. 当前 MiniLM 仅是已跑通的候选模型。用同一份开发 Memory/题目比较小规模候选方案的召回、加载/编码耗时、模型和向量内存占用；资源允许时比较第二个本地 Embedding。若只验证一个模型，如实说明没有比较依据。
5. 根据开发证据冻结模型与版本、编码方式及统一参数；修改配置时同步类型校验和测试。保留主对照共享候选，消融组单列。
6. 与 D 检查必要旧事实可达；由 A/E 将真实结果接到统一服务和 Web，C 不自行重写服务或 UI。

通过标准：至少一条真实开发链路有可核查日志与来源，参数有依据，工作记录包含实际环境/命令/输出及未验证项。没有完整真实产物时不能宣称真实端到端通过；应向组长报告依赖缺口。
