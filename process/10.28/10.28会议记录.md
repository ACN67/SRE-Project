本次会议围绕10月29日至11月1日的模块收尾工作进行安排，重点说明各模块应如何从独立开发过渡到代码交付、审核和分支合并。会议要求优先保证已实现功能可运行、接口可核验，避免在最后几天继续扩大模块功能范围。

## 一、最后半周的开发与收尾安排

结合各模块当时的提交与阶段性工作，会议对后续几天的重点进行了梳理：

| 模块 | 最后半周重点 |
|---|---|
| **A：公共服务及评测** | 收敛三路批量运行、评测指标、统一只读服务和异常处理；补充必要的消融、结果统计和离线自检，整理可供其他成员调用的接口及测试说明。 |
| **B：数据与 Memory** | 完成 Memory 抽取、规范化、构建产物保存、manifest 校验和严格回读；重点检查部分失败、空产物和来源回查，准备向 C 与 A 交付。 |
| **C：查询分析与检索** | 完善查询条件、Embedding 索引、候选检索及 Vector RAG 的输出；核对索引版本、候选范围和检索结果与公共 DTO 的兼容性。 |
| **D：动态状态解析** | 完成关系识别、有效 Memory 选择及 Dynamic 回答的模块内部测试；准备包含调用说明和示例的独立交付产物。 |
| **E：Web 展示** | 收尾 Memory 浏览、原文来源、构建状态与问答展示；准备与 A 的统一服务对接，保留主要页面截图和异常状态展示。 |

后续不再以新增大量功能为主要目标，而是以**接口明确、测试通过、产物能够交接**为各模块收尾要求。已有独立功能应优先补齐必要回归测试和运行说明；依赖其他模块的功能可以先使用受控合成样例验证接口，但必须将正式联调保留为后续任务。

## 二、合并工作的说明

会议再次明确继续采用个人分支开发、通过 Pull Request 审查后合入稳定 `main` 的流程，不直接覆盖其他成员分支，也不因时间接近截止而跳过代码检查。

1. **先确认交付内容。** 各模块负责人整理本分支当前可运行的代码、必要配置、测试和接口说明；缺少的依赖及仍待确定的参数须明确标注。
2. **再核验公共契约。** 重点检查 B→C 的 Memory/manifest、C→D 的候选及分析结果、D→A 的状态/回答，以及 A→E 的只读服务接口，避免只验证单个函数而遗漏跨模块不兼容。
3. **按可审查的批次合并。** 对已通过本模块测试的功能，可分批申请 PR；由相关成员审查 Git 差异、公共 Schema、冲突及 CI 后合并。不能把尚未集成的模块提前写成“项目整体完成”。
4. **合并后再做联调。** 集成分支需要完整复跑合同测试和关键场景，尤其检查跨样本来源、Memory 状态、检索索引版本、时间冲突、无证据和服务故障。必要修复要保留提交与验证记录。

此前已经合入 `main` 的 A/B 基础功能和 E Web 一期仍作为集成起点。后续合并应明确保留已有 README、公共 DTO 和规范化数据文件，不能使用强制推送或整体覆盖的方式处理冲突。

## 三、会议后续安排

10月29日至31日各成员继续完成本模块的最后收尾与自测，尽可能在11月1日前形成稳定、可移交的版本。11月1日再汇总各分支实际完成情况、未解决问题及交付方式，为下一周集中整合联调确定任务。

对于跨模块接口仍有不确定的部分，先记录真实阻塞和负责模块，避免擅自修改其他成员实现。后续的课程 Final Presentation 和最终 Milestone 资料也应在功能收敛后开始整理，包括模块分工、技术实现、实验结果、演示截图和过程记录。具体提交格式与截止时间仍以课程要求为准。
