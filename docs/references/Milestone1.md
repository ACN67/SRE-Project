## 1. 团队角色与职责

采用五人各负责一个技术模块、组长兼任项目协调的模式。每位成员负责本人模块的设计、实现、测试和技术说明，并参与最终系统集成与项目报告。

| 成员 | 角色 | 职责范围 |
|---|---|---|
| **常珂舒** | 评测、基线与集成 | 初始化 GitHub 仓库、邀请成员及维护协作规范；承担评测框架、Full Text 基线和主流程等技术开发工作；协调接口并负责最终集成与交付组织。 |
| **吴宇轩** | 数据与 Memory 构建 | LoCoMo 数据处理、结构化 Memory 抽取、来源追溯与 JSON 导出。 |
| **郭柏村** | 记忆检索 | 相关 Memory 检索、Top-K 结果及 Vector RAG 基线。 |
| **杨林涛** | 状态解析与 QA | RETAIN / UPDATE / SUPERSEDE / CONFLICT 关系判断、有效 Memory 选择和问题回答。 |
| **刘星宇** | Web与可视化 | Web 交互、结构化 Memory 浏览、证据及状态关系展示。 |

## 2. 项目管理与沟通

- **固定会议：** 每周**周三、周日 22:00**，使用腾讯会议；单次不超过 30 分钟。
- **会议组织：** 组长提前汇总议题、创建或发送会议链接并主持会议；会议记录也由组长确认并归档。
- **会议议程：** 各人进度与下阶段计划（约 10 分钟）→ 阻塞和需要模块间问题（约 15 分钟）→ 决议与任务确认（约 5 分钟）。
- **任务追踪：** 使用 GitHub Issues/Projects 或仓库内任务表，记录责任人、预计完成时间与状态；出现依赖风险及时提出，不必等到例会。
- **过程记录：** 仓库设置 `process/` 目录，保存周计划、会议纪要、必要的线上会议截图和决策记录。

**会议纪要最低字段：** 日期与参会者｜已完成事项｜问题与决定｜后续任务（负责人、期限）。

## 3. 版本控制与工作约定

1. 创建 GitHub 仓库并邀请五位成员，成员可修改文档与代码。
2. 从首份交付物草稿开始追踪版本；`main` 保存可用版本，各成员使用独立分支开发，通过 Pull Request 或组内约定流程合并。
3. Commit 信息使用任务描述（如 `feat: add memory extraction`、`fix: correct retrieval output`）；通过 Git 提交者信息和 PR 保留个人贡献记录。
4. 关键交付节点使用版本标签或明确的提交标识；合并前完成基本功能测试。
5. 不向仓库提交 API 密钥、密码、私人数据及不必要的大型模型文件。接口和数据格式变更须通知有关成员。

**前三周以开发为主，第四周用于最终整合、测试和报告。** 具体个人日程由模块负责人自行安排；每周例会检查阶段目标，不以每日任务代替成员计划。

| 周次 | 时间 | 阶段重点 | 周末预期成果 |

| 第1周 | 10.12—10.18 | 仓库初始化、需求整理、模块边界及接口约定；各模块启动开发 | 开发框架、初版接口约定和可运行原型 |
| 第2周 | 10.19—10.25 | 核心功能开发、初步联调及模块测试；形成SRS文档 | 核心功能初版、SRS 与初步测试结果 |
| 第3周 | 10.26—11.01 | 完成主要模块、优化逻辑、运行评测及模块验收 | 基本完备的独立模块与实验数据 |

**缓冲安排：** 各阶段在各自目标日期前预留检查与修复时间；11 月 6 日前完成主要代码，11 月 7 — 8 日进行验证，11 月 9 日核查最终提交。

## 6. 阶段验收与材料归档

- **个人验收：** 模块可运行、输入输出清楚、具有基本测试与使用说明、代码已提交。
- **全组验收：** LoCoMo 导入 → 结构化 Memory → 检索 → 状态解析 → 回答 → Web 展示流程可运行；保存 JSON、评测结果、基线对照与原始证据关联。
- **过程归档：** 文档、计划、腾讯会议记录/截图、GitHub 仓库及提交历史按要求保留。
