# 10月21日会议记录

**时间：** 10月21日 22：00 - 22：23

**会议主题：** Milestone 3 需求文档、Use Case 细化及阶段性代码合并

**参与成员：** 全体成员

本次会议主要围绕 Milestone 3 的软件需求规格说明书（SRS）、典型使用场景的描述方式，以及各模块当前开发进度和后续分支合并需要注意的问题进行了讨论。

## 一、Milestone 3 文档的整理

会议对 SRS 的内容进行了梳理。与 Milestone 2 的项目提案不同，SRS 需要明确系统具体应完成的功能、输入输出、异常处理和验收条件，而不是重复介绍项目背景或详细展开代码实现。文档以现有技术规范和 Milestone 2 已确定的功能范围为基础，按照总体描述、功能需求、非功能需求、数据要求、使用场景和验收追踪等部分组织。

考虑到最终文档的篇幅限制，组内讨论了精简内容的方向：保留主要功能需求与可验证条件，适当压缩背景和技术细节，避免大段重复现有技术文档。Milestone 3 计划以 SRS 文档为主要交付材料；此前的会议记录、提交记录和其他过程资料继续整理，供 Milestone 4 材料打包时使用，具体提交形式仍以课程要求为准。

## 二、Use Case 的讨论

会议重点讨论了 Use Case 应如何描述。Use Case 不应只是重复功能需求列表，而要从实际使用者的角度，说明在什么条件下发起操作、系统如何处理，以及正常和异常情况下应给出什么结果。因此，文档中的每个场景采用表格形式，统一说明使用条件、操作流程和异常处理，便于后续演示和测试时逐项核对。

目前优先保留四类典型场景：浏览 Memory 并回查来源、查询当前状态、查询历史状态、处理冲突或证据不足。其中当前状态与历史状态需要分别描述。例如，同一人物先后出现不同工作记录时，“现在在哪里工作”应根据最新有依据的状态回答，而“过去某个时间在哪里工作”则应使用该时点适用的旧记录，不能简单地把最新信息套用到所有问题中。

对于冲突和证据不足的情况，大家还需要特别注意区分几种结果：确实没有相关证据、问题中的时间无法确定、已有证据互相矛盾，以及系统本身运行失败。这些情况不能都归为“无法回答”，否则无法体现动态记忆管理的特点，也不利于验收。Use Case 中应保留原文来源的查看方式，使回答和状态判断有据可查。

## 三、项目进度与后续合并安排

会议对各模块的进度及分支整合进行了说明。A 的基础 LLM 与公共接口工作已进行了多次合并；B 已完成第一批数据导入、会话规范化和来源回查，并进入后续 Memory 构建工作；E 的 Web 一期已通过 PR 合并到 `main`；C 已有检索相关的独立开发提交。D 模块及各模块的完整联调仍需继续确认，现阶段的基础测试通过不代表整套问答流程已经完成。

随着成员开始陆续提交和合并，后续仍以 `main` 作为稳定集成分支，各人在自己的分支开发。合并前应先检查公共数据结构和上下游接口，完成必要测试、审查及冲突检查；合并完成后，再将最新 `main` 同步到需要继续开发的个人分支。涉及 README、公共契约等多人可能修改的文件，应事先沟通并确定保留版本，避免合并时覆盖他人的工作。未经负责人确认，不应直接修改或改写其他成员分支的历史。

接下来继续完善 SRS 中的使用场景与验收依据，同时推进 B/C/D 的接口对接以及 A/E 的后续服务集成。各成员及时保留提交、测试与问题记录，便于后续的 Milestone 4 过程材料整理。
